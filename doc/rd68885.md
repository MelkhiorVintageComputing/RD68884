# RD68885: the MC68882 build

RD68885 is RD68884 built as an MC68882: `MODEL = 68882` on `rd68884_top`, or `rtl/rd68885_top.sv`. It is the same RTL, the same tests and the same tools, with a second microcode build. The MC68881 build (`MODEL = 68881`, the default) is unchanged by it.

**The goal:**
- the MC68882's instruction overlap, and everything else of the MC68882 that software can see;
- identifying itself as an MC68882;
- timing closed at 71.43 MHz on the IIsiA7 Mini;
- under about 25% of its slices.

**Milestones:**

| | Scope | State |
|---|---|---|
| R1 | The model's plumbing; its frames, its exception rule | done |
| R2 | The golden model's MC68882 (`FPU882`) and the ISS's conversion unit | done |
| R3 | The conversion unit in RTL: the next instruction's dialog while the APU computes | done |
| R4 | Fully concurrent FMOVE | done |
| R5 | Clock counts against FPU Table 8-3, the board at 71.43 MHz, SunOS, the hardware | done |

## What the MC68882 changes

FPU = MC68881UM_split, which describes both chips.

**Overlap** (§5.1.1–5.1.2, §8.2, Tables 5-1, 5-4, 5-5, 5-6 and 8-3):
- A conversion unit (CU) runs the next instruction's dialog, operand transfer and conversion while the APU executes the previous one. At most two instructions are in flight.
- S/D/X operands come in with CA=0 evaluate-EA primitives, which release the main processor as soon as the operand is written.
- Some FMOVEs complete in the CU alone.
- Conditionals, FMOVEM and the control-register moves wait for both units.

**Exceptions** (§6.1, §7.2.2, §7.4.2.5):
- A floating-point exception stays reported past the main processor's exception acknowledge, until its handler clears it in the state frame: FSAVE, then BIU-flags bit 27 set to inactive, then FRESTORE (Fig 5-6).
- The control CIR's AB bit aborts; its XA bit does not.

**Frames** (§6.4.2, Fig 6-5, Table 6-6):
- idle `$1F38` (56 bytes) and busy `$1FD4` (212 bytes), against the MC68881's `$1F18` and `$1FB4`;
- 32 bytes of CU state after the command word;
- the version byte is the same, so software tells the two chips apart by the size byte (§5.2.4, Fig 5-9).

## R1: what is built

**The model:**
- `MODEL` on `rd68884_top`, `rd68884_biu` and `rd68884_seq`.
- `tools/ucode/asm.py` assembles `tools/ucode/program.py` once per model and writes:
  - `rtl/gen/rd68885_ucode_rom.sv` beside `rd68884_ucode_rom.sv`;
  - the MC68882's entry points (`ENTRY82_*`) in the shared package;
  - `build/ucode-68882.json` for the ISS.
- The program sees the model as `p.model`.
- `Machine(model=68882)`, `Core(…, model=)` and `tools/iss/lockstep.py --model` follow.

**Frames:**
- `program.FRAMES` gives each model's format words and lengths.
- The MC68882's idle and busy frames carry eight long words of CU state after the command word. Until the CU exists (R3), they hold ones and FRESTORE skips them.
- FRESTORE accepts only the model's own frames: an MC68881 frame is invalid on an MC68882 (FPU p. 5-14).

**The exception rule:**
- In the BIU, a control-CIR write on the MC68882 aborts unless it is an exception acknowledge without AB while the response is a floating-point exception's take-exception primitive (vectors 48–54).
- Then the primitive and the pending state stay until the handler's FSAVE clears them. The idle frame then carries EXC_PEND, which the handler sets inactive.
- An F-line or protocol violation is acknowledged as on the MC68881, since §5.2.2 says those handlers do not clear anything.
- RD68021 writes `$0002` for an acknowledge and `$0001` for an abort.

**The programs** follow the MC68882's rules, which also hold on an MC68881:
- The floating-point exception handlers clear the exception in the frame. On an MC68881 the acknowledge has already cleared it and the BSET changes nothing.
- A handler's first FPU instruction is FSAVE. `fpu_m4`'s BSUN handler used to set FPCR first, which is a protocol violation on an MC68882.
- The frame checks compare against per-model symbols, `FRAME_IDLE`, `FRAME_BUSY` and `IDLE_SIZE` (the Makefile's `FRAMESYM_*`). Each `.S` program is built once per model (`<name>-68882.hex`).

**Checked:**
- `make check`: `biu_tb` in both models; on the MC68882 a test of the control CIR's two bits.
- `make sys MODEL=68882`: every program on every port, in lockstep with the MC68882 microcode.
- `make sys`: the MC68881 build unchanged.

## R2: the reference model and the ISS

**The golden model** is `cpif.FPU882` (doc/model.md, "The MC68882"). Its tests, in `tools/model/tests/test_882.py`:
- the dialogs, one passage of the manual each;
- 600 random programs run on `FPU881` and on `FPU882` with a slow APU, half of them with exceptions enabled and handled the figure 5-6 way. They must end the same: registers, memory, values stored, conditions, each exception's vector and FPIAR.

**The ISS** (`tools/iss`, model 68882) has the conversion unit in its BIU (`biu.py`) and the MC68882's microcode. `tools/iss/tests/test_overlap.py` holds it to `FPU882`:
- the random programs;
- an idle frame with a held CU instruction, byte for byte;
- a busy frame in the middle of a CA = 0 transfer;
- AB on the CU's dialog;
- an interrupt that saves and restores while a third instruction waits behind an exception-held CU.

## R3: the conversion unit

**The design.** The CU is a few registers and a small state machine in the BIU (`rtl/rd68884_biu.sv`, `rtl/rd68884_cu_decode.sv`), not a second datapath. Conversion stays in the APU: it is a few clocks against a dialog of tens.
- **Its registers:** the command word, the PC passed, the operand's three long words, the long words still to come, and flags: held, released, PC received, B/W/L source.
- **When it takes an instruction:** while the sequencer computes a released instruction (`apu_run`, the microword's `FLAG SET_RUN`, cleared at the idle loop and by every trap). It takes register to register (FMOVECR too) and opclass 010 with a B, W, L, S, D or X source. It also takes a command already latched, once it is free. The sequencer acknowledges latched commands only when `apu_run` is 0, so the two never race.
- **Its first primitive** comes from the BIU itself: `$0900`/`$4900`; `$1504`/`$1608`/`$160C` with CA = 0 (figure 7-19), after which the BIU expects a command at the last operand long word (FPU 7.5.1); `$9501`/`$9502`/`$9504` for B, W and L, then `$8900`.
- **The handoff.** The idle loop takes the CU's instruction before a latched command or a save request (`CU_READY`, then `cu_take`). `BIU CU_TAKE` moves the command word and operand into `CMD` and `XI`, and the PC into FPIAR. The microcode then joins the MC68881's path at the unpacking.
- **An exception** stops the handoff. A CU instruction still in its dialog reports it with `$1D3x`, mid-instruction (`cu_chk`). A released one leaves it to the next instruction, which reports it pre-instruction (`gen_pend`: with an instruction in the CU, FMOVEM and the control registers report too).
- **Frames:**
  - The CU's words (TSRC/TDST `CU`) go in both frames, laid out as doc/model.md says; an empty CU is all ones, and FSAVE leaves it empty.
  - A CU in its dialog makes a busy frame (`cu_bsave`); after FRESTORE, `CU_RESUME` gives the dialog back.
  - A pending instruction in a restored idle frame goes back to the latch (`RELATCH`), behind the CU's.
  - The MC68882's busy frame has the BIU flags last, where figure 5-6's handler sets EXC PEND.
- **Also:** the mandatory PC (EXP_PC, FPU 6.1.12); AB and XA (FPU 7.2.2), with the `abort_ab` entry, which keeps a pending exception.
- **The MC68881 build** has the same RTL with the CU inert, and its microcode does not use the new fields. Its ROM changed in one respect, a fix that applies to both builds: an unread take-exception primitive at FSAVE is saved as the pending instruction, as the model always had it. Without it, an interrupt taken just as a latched instruction got its exception lost that instruction.

**Three races the RTL settles** (the ISS's accesses are atomic; only the second can happen there too):
- The main processor can read a primitive asking for the PC in the clock the sequencer rewrites the response. The PC is then still expected: from the value read, not from `resp_read_o` (`fpu_m10`).
- The sequencer can post its next primitive before the main processor has written the PC. The PC still comes first: the write sets what is expected after it (`fpu_m10`).
- The main processor can read the CU's first primitive in the clock of the APU's end-of-instruction write, which stands aside. Only a write that takes effect masks the read event now (`fparith`).

**Size**, Vivado out of context on the xc7a35t: 4,949 LUTs and 1,082 flip-flops, against 4,492 and 921 for the MC68881 build (+457 LUTs, +10%), and WNS 4.97 ns against 5.09 ns.

**Checked:**
- `biu_tb` (`t_cu`), on every port size, for both MC68882 builds: the CU's dialogs, the latched third instruction, B/W/L, the PC to FPIAR at the take, AB, FRESTORE of CU words, the relatch.
- `sim/programs/fpu_m10.S`, built for both models (`MODEL` in the Makefile's `FRAMESYM_*`):
  - overlapped instructions;
  - a mid-instruction report (a busy frame on the MC68882);
  - a held CU instruction in the idle frame;
  - a bus error in a CA = 0 transfer;
  - AB on the CU's instruction;
  - a conditional after overlap.
- `make sys MODEL=68882`: every program, every port, in lockstep with the ISS.

## R4: the fully concurrent FMOVEs

FPU table 5-5: while the APU computes, the CU completes three FMOVEs by itself.
- **`FMOVE <ea>,FPn` from S, D or X:** the CU converts the operand it collected (`rtl/rd68884_biu.sv`) and writes FPn through the register file's second port.
- **`FMOVE FPm,FPn`:** it reads FPm through that port and writes FPn.
- **`FMOVE.X FPm,<ea>`:** it reads FPm, packs it, and answers the evaluate-<ea> primitive with CA = 0 (`$320C`, figure 7-21). The main processor reads the three long words and goes on.

**Downgrades.** In any of these cases the instruction takes stage A's path, through the APU. A store not completed this way goes back to the command latch: the main processor is polling `$8900`, as it would for any latched command.
- (a, f) a register conflict with the APU instruction's destination (FPn, and FSINCOS's FPc);
- (b) a NaN, denormal or unnormal value;
- (c) single or double rounding precision;
- the model's choice: an exception enabled.

**FPSR in program order.** An FMOVE the CU completes clears the exception byte and sets the condition codes; an extended store clears the exception byte only. The BIU holds these (`dcc`). The sequencer applies them once no released instruction computes (`RUN` low, `dcc_ack`): after the older instruction's own FPSR update, before any younger one's. Condition codes and the exception byte therefore come out as in sequence, and the older instruction's accrued exceptions stay.

**Handoff.** `CU_READY` hides an FMOVE the CU is about to complete while the APU computes, so the sequencer and the CU never both take it.

**The extended store without overlap** also uses CA = 0 when its source is normal, zero or infinite (`out_x0` in `arith_ucode.py`). The BIU counts its operand reads, as it counts a CA = 0 load's writes. S and D stores keep the MC68881 dialog (the plan).

**The register file** (`rtl/rd68884_regfile.sv`) is true dual-port in the MC68882 build (`PORT_B`). The port's read register is a fourth named exemption in `tools/reset_audit.py`, for that build only.

**Checked:**
- `tools/iss/tests/test_overlap.py`: a directed test in which each of the three completes in the CU, a conflict waits, and FPSR ends in program order, against `FPU882`; and the random programs, where all three occur.
- `fpu_m10` section G on the RTL, in lockstep: the CU wrote the registers through port B and read for the store. FETOX gives it the time: the FPU's clock is three times the CPU's here, so a short instruction is over before the next one's operand is in.
- `make sys`, both models.

**Size**, Vivado out of context on the xc7a35t: 5,728 LUTs and 1,286 flip-flops, 22 block RAMs. Stage B costs 779 LUTs on top of stage A's 4,949, mostly the operand conversions and the multiplexers into the CU's registers. WNS is 4.97 ns. The MC68881 build, with the register file rewritten into one address per port, is 4,382 LUTs (4,492 before, within synthesis noise of about 100 LUTs). The board build decides whether this fits (R5).

**A fix found on the way:** `make sys` let a lockstep failure through, because its status was lost in a pipe. It now fails the run.

## R5: timing, the board, SunOS, the hardware

**Clock counts** (`make cycles MODEL=68882`, doc/timing-divergences.md "The MC68882 build"):
- each arithmetic and FMOVE row's total, head and tail, against FPU Table 8-3, frozen in `tools/cycles-68882.frozen`;
- the fully concurrent FMOVEs have a head as long as their total, as in the table;
- S and D stores have none, by the plan's choice.

**The board** (doc/boards.md): `make board-iisia7 MODEL=68882 BOARD_DIVIDE=14` meets timing at 71.43 MHz (+0.071 ns) in 1419 slices, 17.4% of the xc7a50t, under the 25% the plan allowed.

**SunOS** (`make sunos MODEL=68882`, doc/system.md): SunOS 4.1.1 boots in TME on RD68021 with RD68885 as its FPU (`build/tme-68882`, `build/sunos-68882`). It runs the C program compiled with `cc -f68881`, and the 82 lines of console output match TME's own m68020 with an MC68882 (`fpu-type m68882`), time stamps aside. RD68885 answered 852 general and 57 conditional instructions, 1252 FSAVEs and 627 FRESTOREs.

**The MC68881 build**, after all this: `make check`, `make sys` and `make cycles` pass. The frozen clock counts did not move.

**The hardware:** in a Macintosh IIsi, with `rd68885_iisia7.mcs` (71.43 MHz) in the IIsiA7 Mini's flash, RD68885 works as the machine's FPU.
